Commentary: I likely followed the return path of the text printing and needed to understand the function call that happend BEFORE where we returned.
It is obvious when, after a RET, you don't see a CALL that there is some "acyclic" return path.
I think part of rom 2 did not initially decompile correctly. Later, I think I found this to be sections of const data (addresses of other functions / lookup tables) embedded alongside function code.
I knew based on the analysis of the text functions that I returned to 0xCxxx (the ram function location). Finding the source of the code was easy, just a search away.
  However, I thought I could just run the decompiler anywhere and it would "magically" decompile the region based on heuristics of arguments.
  This ended up causing more trouble as I needed to decompile each function one at a time (it probably would have been easier to patch the original rom's RAM region with the code and optimistically try a decompile)
Revisiting this "before" function and correctly clearing + analyzing the code, I could now see the dynamic PUSH + RET calling convention.
However, there were TWO of these functions. The parent (scene_dynamic_progress) and the child (scene_dynamic_ramfunc).
I have formed a link that XREF could not show me.
Also, when you place a breakpoint in the parent dynamic RAM func (scene_dynamic_progress), I think the registers were mostly the same. This can mislead you into thinking that "this function seems to be doing the same thing over and over"
This likely also gave me the idea that I may need to decompile/recompile MORE incorrectly decompiled code to find more XREFs
